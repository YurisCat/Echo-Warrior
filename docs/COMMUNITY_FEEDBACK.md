## 核对方式

1. 读取分页、折叠正文和全部楼中楼。不能用首页片段或搜索摘要代替全量检查；MC 百科同时检查喷泉广场与冒险者公会。
2. 记录日期（Asia/Shanghai）、作者、评论 ID／楼层，以及玩家诉求和作者回复的对应关系。只提炼与项目有关的内容，普通称赞、玩笑、私人近况与祝福不进入开发待办。
3. 分开标记：**明确承诺、认可但未定方案、有条件考虑、玩家单方面愿望、已发布、部分满足、待复现／待验收、未承诺／倾向不做**。
4. 对照 `PROJECT.md`、`CHANGELOG.md`、正式发布记录和必要源码。等级上限可配置不等于所有数值可配置；源码有入口不等于默认功能可见；旧回复的“开发版已修”要继续查是否已经发布。
5. 本次公开源码／正式版状态优先于旧候选历史。发现 `PROJECT.md` 的历史段落仍写“未发布”时，核对同文件的正式发布段及 `docs/releases/`，不要据旧措辞重复列债。
6. 建议只能作为更新候选，不自动变成已批准范围。缺少复现材料的报告保留问题状态，不擅自宣布根因或已修。
7. 后续检查既看新主楼，也重看旧楼的新回复；将新增、兑现、继续等待的事项与上次报告对照。无法读取时写清缺口，不声称已经读完。
8. “查看留言”只授权读取与本地整理。发布回复、私信、修改站外介绍或承诺排期，需要用户另行明确指示。

## 本次取数经验

- Firefox 现有会话可读取三站；普通网页抓取对动态评论不完整，B 站评论的 Shadow DOM 还可能停在加载状态。
- CurseForge 评论页实际使用 `/api/v1/mods/1677436/comments?page=0&size=20`，页码从 0 开始。返回值内含递归回复；页面边界可能把延续回复放在下一页，必须按 ID 去重并结合上下文，不能将每个顶层返回对象都当成独立话题。
- B 站主列表使用 `/x/v2/reply`，`type=1`、`oid=117399810476318`；内嵌的 `replies` 只是预览。使用 `/x/v2/reply/reply` 按主楼 `root` 读取完整回复，并核对数量。2026-11-11 和 11-13 均为 17 个主楼加 22 条回复，合计 39。
- MC 百科页面的 `get_comment` / `get_reply_comment` 分别调用 `CommentRow` / `CommentReply` 读取接口；虽然 HTTP 方法为 POST，其用途是读取分页。主楼每页 20 条、楼中楼每页 5 条，不能假定楼中楼已全部显示。
- 这些接口属于 2026-11-11 观察、11-13 再次核实的网站实现，后续仍应先核实，不当作永久接口契约。只在浏览器内使用会话，不导出 Cookie、令牌或其他私人浏览数据。
- 比较 MC 百科旧正文时先排除自动生成的站外链接脚本／DOM ID，避免误判评论被编辑；CF 按正文非空数与页面计数核对，空白记录单独记载。
