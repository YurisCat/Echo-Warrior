# Echo Warrior 多版本移植与防回退手册

## 1. 目的

本文档保存能够跨 Minecraft 版本、加载器或依赖版本复用的移植经验。它回答的是：

- 某类问题为什么会在旧版本再次出现。
- 移植时必须检查哪些语义、资源和生命周期差异。
- 哪些检查应当自动执行，哪些必须由人观察。
- 修复一次之后，怎样避免在下一条兼容线重新踩坑。

本文档不是玩法设计来源、版本更新日志或逐次 Bug 流水账。

## 2. 文档职责边界

| 载体 | 负责内容 | 不负责内容 |
| --- | --- | --- |
| `PROJECT.md` | 当前玩法规则、范围、依赖、兼容目标和已批准决策 | 详细调试过程和每次失败尝试 |
| 本手册 | 可复用的移植根因、规则、检查方法和版本差异 | 当前候选包状态和面向玩家的发布说明 |
| `scripts/check-<version>-baseline.ps1`、GameTest、自测命令 | 可确定、可重复的机器检查 | 画面、声音和手感判断 |
| `docs/COMPATIBILITY_<version>_TEST_CHECKLIST.md` | GUI、动画、声音、操作手感、真实多人等人工签收 | 代替自动构建或服务端状态断言 |
| `CHANGELOG.md` | 对外发布时值得玩家知道的变化 | 内部测试版本的完整诊断历史 |
| 回声档案馆 | 玩家可见的玩法、控制、数值和状态规则 | 纯工程迁移方式和内部工具变化 |

任何玩家可见规则都以 `PROJECT.md` 为准；本手册不得自行扩大玩法范围。

## 3. 什么时候维护本手册

修复 Bug 后，满足以下任一条件时，必须在同一任务更新本手册：

- 根因可能在另一 Minecraft 版本、另一加载器或另一依赖版本再次出现。
- Fabric 与 NeoForge 的生命周期、网络、注册或客户端接口存在实质差异。
- 问题涉及保存数据、服务端权威、菜单并发、实体代次或跨维度状态。
- 问题涉及资源目录、模型格式、渲染批次、Mixin、类加载或专用服务器安全。
- 表面症状与真正根因差距较大，未来容易误诊。
- 同类问题已经发生过回归，或者仅靠代码审查很难确认。
- 修复形成了新的自动断言、GameTest、专服自测或人工复测规则。

以下情况通常不写入本手册：

- 单纯错别字、一次性版本号或没有迁移价值的局部重命名。
- 尚未复现、尚未定位根因的测试员描述。
- 临时诊断日志、失败实验和最终没有采用的方案。
- 只影响某一个内部候选包、且不会改变以后移植决策的打包失误。

未定位的问题先进入对应版本的人工测试清单或问题记录；根因确认后再决定是否沉淀到这里。

## 4. 每个 Bug 的维护决策

每次确认并修复一个 Bug，按以下顺序处理：

1. **当前规则是否改变？**
   - 是：更新 `PROJECT.md`。
   - 若同时改变玩家可见玩法、控制、平衡值或状态，再更新回声档案馆。
2. **根因是否可跨版本复用？**
   - 是：更新本手册对应条目；没有合适条目时新增。
3. **能否由机器稳定判断？**
   - 能：增加或更新基线脚本、单元测试、GameTest、自测命令或集成测试。
   - 不能：把最短、可复现的观察步骤加入人工清单。
4. **是否影响对外交付？**
   - 是：在正式发布时更新 `CHANGELOG.md`。
5. **是否只是当前候选包的修复历史？**
   - 是：放在对应版本状态记录中，不把整段调试过程复制到本手册。

因此，维护策略不是“每发现一个 Bug 就无条件向本手册追加一段”，而是“每次修复都执行一次分类，自动维护真正有长期价值的部分”。

## 5. 新增经验条目的最低格式

新增或扩充条目时至少写明：

- **症状**：玩家或测试端实际看到什么。
- **根因**：哪个版本、加载器、生命周期或权威边界造成问题。
- **移植规则**：以后应当做什么，不能只写这次改了哪个类。
- **自动守卫**：由哪个脚本、测试或 JAR 审计检测；没有时写“暂无”。
- **人工签收**：仍需观察哪些画面、声音、手感或多人行为。
- **适用范围**：共享规则、特定 Minecraft 版本、加载器或依赖版本。

推荐格式：

```markdown
### PORT-XXX 简短标题

- 症状：
- 根因：
- 移植规则：
- 自动守卫：
- 人工签收：
- 适用范围：
```

已有条目能够覆盖新问题时，优先扩充原条目，不制造重复条目。

## 6. 固定移植流程

### 6.1 开始之前

1. 阅读 `PROJECT.md`、本手册和目标版本 README。
2. 明确主线版本、目标版本、两个加载器、Java 和依赖版本。
3. 建立功能清单，而不是按文件名机械复制。
4. 标出玩家可见功能、服务端状态、客户端表现、资源和数据五个层面。
5. 确认目标版本是否需要独立存档和运行目录；默认不得把高版本世界降级打开。

### 6.2 推荐实施顺序

1. 构建系统、加载器元数据和专用服务器安全。
2. 注册表、数据组件或旧版等价存储、菜单和网络通道。
3. 保存数据、UUID、绑定代次和跨维度恢复。
4. 一条完整纵向切片：物品 → GUI → 实体 → AI → 战斗 → 动画 → 保存。
5. 公共玩法系统与其他英雄。
6. 模型、动画、纹理、声音、本地化、配方、标签和创造栏。
7. 自动基线、专服自测、经授权的客户端启动检查和人工签收。

### 6.3 完成定义

一条兼容线只有同时满足以下条件才算完成：

- 两个加载器从同一候选版本构建出独立 JAR。
- JAR 内只包含对应加载器元数据，不混入另一加载器入口。
- 专用服务器能够启动、自测并正常关服。
- 注册、保存、网络和权威状态有自动断言。
- 玩家可见资源与本地化经过 JAR 内容审计。
- 画面、声音、控制和多人体验有明确的人工清单。
- 已解释所有主线独有文件：是功能遗漏，还是目标版本格式不适用。
- 没有把自动测试通过误写成人工观感已经签收。

## 7. 固定审计矩阵

每次新增兼容版本或同步完整功能节点时，至少检查以下项目。

### 7.1 构建与加载器

- Java 字节码版本与目标运行时一致。
- Fabric/NeoForge 元数据、入口点、依赖和客户端入口互不串包。
- 共享类不直接引用只存在于某一加载器的 API。
- 客户端类和客户端 Mixin 不会被专用服务器加载。
- 构建、运行目录、日志和测试世界与其他版本隔离。

### 7.2 注册与内容目录

- 物品、方块、方块实体、菜单、实体、声音、粒子、创造标签均已注册。
- 创建了对象不等于玩家可取得：同时检查创造栏、配方、战利品、交易或命令入口。
- 注册数量、稳定 ID 和文化/稀有度/生物群系标签与主线功能清单一致。

### 7.3 资源与本地化

- 模型、纹理、动画、声音、技能图标、状态图标和字体使用目标版本支持的格式。
- 中英文键集合和值按需要比较；同时审计代码真实调用点、描述行数和状态分支。
- 资源存在不代表渲染可见：颜色提供器、透明层、绘制层级和批次提交单独检查。
- 主线独有资源文件必须逐项解释，禁止仅凭目录差异认定遗漏。

### 7.4 网络、菜单与创造模式

- 服务端对物品、绑定、燃料、技能、饰品和模式拥有最终权威。
- 客户端预测只提供即时观感，不得成为最终保存来源。
- 菜单保存多个关联槽时应原子提交，不能分次写回互相覆盖。
- 长时间打开的菜单必须检测服务端状态修订，拒绝旧状态覆盖新状态。
- 创造物品栏的包装槽、快捷栏映射和垃圾槽必须单独测试，不能假设与生存菜单一致。

### 7.5 保存与实体生命周期

- 物品容器组件和世界 SavedData 的权威关系明确。
- UUID 重复、实体代次、未加载实体、跨维度恢复和旧投射物失效均有测试。
- 修改 schema 前明确是否支持已公开存档；内部开发世界可以重建时必须写清。
- 失败事务能够回滚物品、燃料和绑定状态。

### 7.6 AI、战斗与动画

- 服务端命中时刻、朝向、动作状态与客户端动画使用同一时间预算。
- 不同 GeckoLib 版本必须核对触发动画、速度、累计时间和过渡语义。
- 动画首尾帧连续不等于状态切换连续；仍需检查时间轴倒拨和空档。
- 视觉注视、程序化骨骼与模型动画的父骨骼补偿按目标模型重新验证。
- 自动测试验证状态和伤害，人工测试验证抽搐、衔接、速度与观感。

### 7.7 GUI 与视觉反馈

- GUI 原始纹理尺寸、缩放、容器坐标和屏幕绝对坐标不得混用。
- 工具提示应在所有图标之后绘制，保持最高层级。
- 自定义粒子、斜光和覆盖层必须检查深度、批次刷新及实际目标槽坐标。
- 物品渲染与落地方块可能具有不同世界上下文、朝向和初始化时机。
- 自定义消息、动作栏、标题抖动和淡出等反馈需检查是否重复显示原版版本。

## 8. 已确认的可复用经验

### PORT-001 本地化资源齐全不代表界面已经迁移

- 症状：资源文件中存在中文和英文文本，游戏仍显示翻译键、缺少描述或行数不完整；Shift 展开提示也可能遗漏当前装入的英灵等运行时状态。
- 根因：兼容界面没有调用对应键、使用了过时键、描述行数仍按旧实现读取，或只迁移静态说明而遗漏空/非空等状态分支。
- 移植规则：同时比较语言文件键值和所有玩家可见调用点；状态型技能和物品提示必须覆盖每个状态分支，并把当前权威物品组件转换为本地化名称。
- 自动守卫：跨版本双语键比较、源码调用点、状态分支和描述行数断言。
- 人工签收：悬浮全部技能、天赋、状态、按钮及空/已装入状态物品，检查换行与层级。
- 适用范围：所有版本和加载器。

### PORT-002 注册、资源、取得入口必须作为一个整体迁移

- 症状：物品类存在但创造栏不可见，或进入游戏后出现紫黑格、无配方、无标签。
- 根因：只迁移 Java 注册，遗漏模型、纹理、创造标签、配方、战利品或交易入口。
- 移植规则：按稳定内容 ID 建立清单，逐项覆盖注册、资源、本地化、配方、标签和取得路径。
- 自动守卫：JAR 内容清单、注册数量、配方和标签解析。
- 人工签收：创造栏分类、配方书、交易和实际掉落。
- 适用范围：所有内容型移植。

### PORT-003 依赖版本决定资源目录和动画语义

- 症状：召唤实体后客户端崩溃、模型缺失，或动画在状态切换时倒拨和抽搐。
- 根因：GeckoLib 5 与 GeckoLib 4 的资源目录、控制器速度和累计时间处理不同。
- 移植规则：按目标依赖源码和文档适配；1.21.1 GeckoLib 4.9.2 使用 `assets/<modid>/geo/` 与 `assets/<modid>/animations/`，不能机械复制高版本加载路径。动画速度必须在同一触发动画期间保持一致时间基准。
- 自动守卫：JAR 路径审计、模型类路径断言和动作状态自测。
- 人工签收：首次动作、连续动作、释放瞬间、收势和转火。
- 适用范围：使用不同 GeckoLib 主版本的兼容线。

### PORT-004 Mixin 包必须只包含 Mixin 类型

- 症状：客户端启动阶段出现 `IllegalClassLoadError`，普通反馈数据类也被 Mixin 子系统处理。
- 根因：普通类、内部类或记录类型位于 Mixin 配置包下。
- 移植规则：Mixin 包只放 `@Mixin`、Accessor 和 Invoker；粒子数据、算法和状态容器放在普通客户端包。
- 自动守卫：JAR 基线拒绝 Mixin 包中的非预期类和嵌套辅助类。
- 人工签收：无。
- 适用范围：所有使用 Mixin 的版本。

### PORT-005 创造物品栏不能复用生存菜单假设

- 症状：创造模式把遗物或饰品放入召唤器后被吞、复制、放错槽或重开恢复；把召唤器投入垃圾槽、对垃圾槽 Shift+左键批量清空、直接 Shift+左键快速删除、拿到鼠标后点回创造物品列表、带着鼠标物品关闭界面，或加载保存的快捷栏覆盖原槽后，物品已经消失但绑定英灵仍然存活；生存模式正常。
- 根因：创造分类页和“生存物品栏”页使用包装槽与不同编号映射，原版后续点击路径还可能覆盖客户端修改。更关键的是，创造菜单的“销毁”不是单一按钮事件：垃圾槽、普通槽快速删除、创造目录替换鼠标物品、关闭界面丢弃鼠标物品和快捷栏预设覆盖属于不同代码分支；其中一些只清空客户端鼠标栈。把绑定清理写成按钮特判必然持续漏边缘路径，而客户端点击意图也不等于服务端已经删除物品。
- 移植规则：在真实点击入口识别目标库存槽，取消冲突的原版后续路径，通过加载器网络桥让服务端重新验证并权威提交。永久销毁应按语义判断：在非 `THROW`、非窗口外丢弃操作前后，对玩家库存和创造菜单鼠标栈中的召唤器 UUID 做差集，并将批量垃圾槽等异步路径的点击前候选并入；关闭界面和加载快捷栏预设也必须执行同一差分。客户端只报告候选 UUID，服务端必须同时观察真实创造槽移除，延后一刻确认该 UUID 已不在任何在线玩家库存、末影箱、当前打开容器、鼠标物品、已加载掉落物或带库存实体（含原版容器/收纳袋嵌套内容）中，才销毁绑定。槽移除凭据应覆盖玩家可能把物品拿在鼠标上的合理时长，并在同 UUID 重新出现时撤销。普通搬运、装箱、Q 丢弃或拖出窗口即使一度离槽，也必须因没有销毁请求或最终仍可见而保留绑定。
- 自动守卫：自动客户端用两种创造页面执行真实 `slotClicked`，集成服务器读取最终容器组件；另准备两只已经生成实体和绑定的召唤器，分别执行真实 `QUICK_MOVE` 快速删除，以及“热键栏拿到鼠标后点击创造目录”的两阶段销毁，同时断言客户端槽/鼠标为空、服务端绑定删除且实体不再加载。源码基线检查操作前后 UUID 差分、`THROW` 排除、关闭界面、快捷栏预设覆盖、垃圾槽异步候选、服务端槽移除确认、延迟全局可见性复核、打开容器与掉落物扫描；专服自测继续验证嵌套召唤器发现。
- 人工签收：快速连续投入、冲突槽、关闭重开、退出重进、垃圾槽单件销毁、垃圾槽 Shift 批量清空、普通槽直接 Shift+左键删除、鼠标拿起后点回创造目录、拿起后关闭界面、数字键覆盖与加载保存快捷栏；另确认普通移动、Shift 搬运、装箱、Q 丢弃、拖出窗口和正常掉落物均不误销毁。
- 适用范围：1.21.1 及其他创造菜单结构不同的版本。

### PORT-006 关联菜单状态必须原子提交并带修订号

- 症状：取出饰品后关闭 GUI，重开又出现原物品；关闭的技能被旧菜单恢复；两个关联槽互相覆盖。
- 根因：遗物和饰品分次保存、客户端镜像回写，或旧菜单不知道服务端状态已经变化。
- 移植规则：关联内容一次原子提交；持久化 `stateRevision`，旧菜单点击时拒绝写入并重新载入服务端权威状态。
- 自动守卫：SavedData 往返、修订递增、过期菜单合并和不复制自测。
- 人工签收：多人同时修改、关闭重开和重进服务器。
- 适用范围：所有具有长期打开 GUI 和外部状态变化的版本。

### PORT-007 客户端反馈不能取代服务端结果

- 症状：按钮显示成功但服务器拒绝，或失败时没有具体原因；客户端先播放反馈后状态回滚。
- 根因：界面只按本地预测显示结果，没有等待服务端动作码。
- 移植规则：服务端返回稳定动作结果，客户端只根据同步结果显示召唤、遣散、切换和失败原因；本地预测只用于无权威影响的即时视觉。
- 自动守卫：菜单动作码、翻译键和服务端失败分支断言。
- 人工签收：缺少遗物、燃料不足、数量上限、无安全位置和过期状态。
- 适用范围：所有菜单与快捷操作。

### PORT-008 GUI 可见性取决于最终绘制批次

- 症状：日志证明斜光或粒子已经创建并渲染，但屏幕上完全不可见；工具提示被技能图标遮挡。
- 根因：顶点进入了错误的深度层或共享批次，随后被物品图标覆盖；工具提示提交时机过早。
- 移植规则：先刷新容器/物品批次，再用目标版本等价的无深度 GUI 覆盖层绘制并立即刷新；悬浮提示延迟到全部内容之后。
- 自动守卫：绘制层、`flush` 和目标槽锚点源码断言。
- 人工签收：不同 GUI 缩放、创造栏和普通容器中观察实际层级。
- 适用范围：1.21.1 GUI 渲染及其他批次 API 不同的版本。

### PORT-009 方块物品渲染有独立生命周期和朝向

- 症状：动态箱体在创造栏首次显示时崩溃，或箱体存在但正面卡扣不可见。
- 根因：客户端注册阶段过早烘焙原版模型层；无世界物品渲染错误沿用方块世界朝向。
- 移植规则：依赖原版模型层的渲染器延迟到首次实际渲染构造；物品展示明确使用与原版同类物品一致的固定朝向。
- 自动守卫：延迟构造和无世界朝向源码断言。
- 人工签收：创造栏、背包、手持、展示框和落地方块分别观察。
- 适用范围：自定义方块实体物品渲染。

### PORT-010 资源格式差异不能通过机械复制解决

- 症状：目录比较显示主线多出大量文件，误判为旧版本漏包；复制后旧版本无法解析或重复定义模型；主线用选择属性实现的动态物品图标在 1.21.1 退化为永远不变的静态图标。
- 根因：Minecraft 1.21.6+ 的 `assets/<modid>/items/*.json` 与 1.21.1 的 `models/item` 属于不同物品定义体系；新版 `select` 属性不能被旧版模型覆盖系统自动理解。
- 移植规则：比较最终功能语义和目标版本 JAR 所需资源，不要求文件树逐字相同；每组主线独有文件必须有明确版本解释。新版动态选择属性迁移到 1.21.1 时，必须显式注册 `ItemProperties` 数值谓词并建立有序的旧版 `overrides`，同时补回新版属性包含的显示上下文约束，避免 GUI 图标状态污染第一/第三人称模型。
- 自动守卫：目标版本资源清单、已知差异白名单，以及动态谓词注册、各状态覆盖数量/顺序/模型目标和 GUI 上下文源码断言。
- 人工签收：最终物品模型、覆盖状态和颜色；按键触发时逐一检查所有动态状态，并确认手持、掉落与展示框等非目标上下文保持默认模型。
- 适用范围：跨资源格式边界的 Minecraft 版本。

### PORT-011 首次召唤是可回滚事务

- 症状：英灵生成在墙内、危险方块或无站立空间处；失败后燃料仍被扣除。
- 根因：先提交燃料和绑定，再直接使用未验证位置生成实体。
- 移植规则：先寻找完整碰撞箱安全落点；若已经预扣燃料，任何生成失败都必须回滚。不能把“实体创建成功”与“安全放置成功”视为同一件事。
- 自动守卫：安全落点搜索、失败枚举和燃料退还断言。
- 人工签收：狭窄、墙后、熔岩、窒息和恢复安全空间后的再次召唤。
- 适用范围：所有实体召唤版本。

### PORT-012 保存数据必须独立于物品是否加载

- 症状：召唤器放入箱子或区块卸载后，英灵状态丢失、复制或跨维度恢复错误。
- 根因：把物品副本当作唯一状态来源，或旧实体/投射物没有绑定代次。
- 移植规则：世界 SavedData 保存权威绑定；物品只保存可携带镜像。重建时递增或验证代次，使旧实体和旧投射物失效。
- 自动守卫：完整 NBT 往返、未加载绑定、重复 UUID、代次和跨维度快照自测。
- 人工签收：容器保存、重登、跨维度及多人控制者状态。
- 适用范围：所有持久化召唤系统。

### PORT-013 客户端表现与专用服务器安全必须分开验证

- 症状：客户端正常但专服因客户端类引用崩溃，或专服通过却漏掉模型、Mixin 和 GUI 问题。
- 根因：只测试一种运行环境。
- 移植规则：每个加载器至少执行构建/JAR 审计和真实专服启动；客户端启动及资源检查在得到授权后独立执行，视觉仍由人工签收。
- 自动守卫：双加载器构建、隔离专服自测、可脚本化客户端 Quick Play。
- 人工签收：GUI、模型、声音、动画和真实联机。
- 适用范围：所有双加载器兼容线。

### PORT-014 自定义消息需要同时迁移触发语义和呈现层

- 症状：功能消息仍能出现，但退化为原版动作栏；颜色、逐字抖动、淡出或悬浮标题反馈缺失。
- 根因：只迁移服务端翻译键与发送调用，没有迁移目标版本的客户端拦截和渲染层。
- 移植规则：列出全部消息键、触发条件、持续时间和视觉语义；客户端只接管本模组精确键，不能吞掉其他动作栏消息。方向脉冲状态与通用消息状态分离，换手或放回背包不能提前清除已经触发的消息。
- 自动守卫：消息键集合、时长常量、精确拦截和 Mixin 打包断言。
- 人工签收：六类消息、无重复原版文字、换手、静音及悬浮标题。
- 适用范围：回声罗盘及未来自定义 HUD 消息。

### PORT-015 物品组件同步不能被第一人称渲染器误判为换手

- 症状：手持教程手册或知识碎片集翻页，或手持召唤器同步燃料、遗物和饰品时，第一人称手臂反复下沉、抬起或重播使用物品动作。
- 根因：页码书签和召唤器状态写入物品组件后，目标版本的手持渲染器把新 `ItemStack` 快照当成另一件物品，而不是同一物品的状态更新；只为一种书本加例外会让其他同样保存书签的物品继续复发。
- 移植规则：盘点所有会在手持 GUI 操作期间原地更新组件的物品，并为其定义稳定物理身份。召唤器按 UUID 比较；单件教程手册在手中只变更书签时按同一注册物品处理；知识碎片集比较实际页面与数量、忽略阅读书签。确认身份相同后更新渲染器内部快照，不重置装备进度；真实换成另一 UUID 的召唤器、内容不同的合集或其他物品仍执行原版动画。
- 自动守卫：源码基线检查主副手快照更新与各身份辅助函数，专服自测分别验证教程页码和知识合集书签变化仍被识别为同一手持物、不同物品不会误判。
- 人工签收：教程手册与知识碎片集在主手、副手连续翻页和切换章节，召唤器多类组件同步，以及真实换物动画。
- 适用范围：1.21.1 与 26.1.2 的 `ItemInHandRenderer`，以及未来使用组件同步的手持 GUI 物品。

## 9. 当前版本差异基线

| 项目 | 26.1.2 主线 | 1.21.1 兼容线 | 移植含义 |
| --- | --- | --- | --- |
| Java | 25 | 21 | 分别审计字节码，不共享运行时假设 |
| GeckoLib | 5.5.2 | 4.9.2 | 资源目录、控制器和动画时间语义需要适配 |
| SmartBrainLib | 2.0.0 | 1.16.11 | 行为 API 不能机械复制，保持行为结果一致 |
| 物品资源 | 新物品定义体系 | `models/item` 覆盖体系 | 比较功能结果，不要求文件树一致 |
| Fabric/NeoForge API | 26.1.2 对应 API | 1.21.1 对应 API | 注册、网络、渲染和生命周期分别适配 |
| 工程位置 | 根目录模块 | `versions/1.21.1/` | 运行目录、世界和构建产物严格隔离 |
| 日常开发 | 优先 26.1.2 Fabric | 完整节点统一同步 | 不把主线逐次试错实时复制到旧版 |

新增 1.20.x 等兼容线时，应在本表增加新列或另建清晰的版本矩阵，不覆盖已有结论。

## 11. 开始下一条旧版兼容线时

在正式实现 1.20.x 前，先完成一个只读技术验证：

1. 确认目标小版本、Java、Fabric、NeoForge、GeckoLib 和 SmartBrainLib 的可用组合。
2. 列出注册、数据组件/旧 NBT、网络 payload、菜单、渲染、数据包和世界生成 API 的断层。
3. 选择一个纵向切片验证构建、双专服、保存、实体、GUI 和模型。
4. 依据本手册建立该版本的基线脚本与人工清单。
5. 在纵向切片稳定前，不承诺五英灵全量迁移，也不引入新玩法。

如果第二条旧版兼容线导致大量版本条件和重复文件，再按 `PROJECT.md` 的决定重新评估 Stonecutter；不能仅为了减少目录数量牺牲审计清晰度。
