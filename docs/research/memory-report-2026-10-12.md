# 0.2.7 内存反馈调查

日期：2026-10-12（Asia/Shanghai）。作者提供两条 CurseForge 评论并要求在 FOXY-NODE 排查。一条称「0.27」游玩约一小时后占满 32 GB 并持续 GC 卡顿，另一条称新版内存占用明显上升。目前按本项目正式版 **0.2.7** 排查；反馈者的 Minecraft 版本、加载器、Java 参数、整合包、TBF 使用情况及日志尚未提供。

## 证据边界

- 评论是待复现报告，不能据此确认内存泄漏，也不能先归因于 TBF。
- 本轮直接测试已发布 JAR，未重编同名正式包。源码审计基于 `2993cb64ad2f3c2a243c1ffcdf8ba648fd9b0c34`；工作区原有的百科投稿和配音草稿不属于本轮变更。
- 所有游戏运行位于 FOXY-NODE 的隔离快照和测试世界。没有读取反馈者或作者的玩家存档，没有发布修复包。
- 诊断使用 JDK `jcmd`、JFR、Native Memory Tracking 及 Windows 进程内存计数。临时 Java agent 仅在指定测试 JVM 中调度测试操作及读取状态，不注册字节码 transformer，不修改正式 JAR。
- `GC.class_histogram` 会主动执行完整 GC；这些检查引起的停顿与自然 GC 分开统计。判断重点是回收后的存活对象、堆基线及进程私有内存，不把 JVM 的预留地址空间、已提交堆或累计分配量当成泄漏量。
- 方法依据：[Oracle Java 内存泄漏排查](https://docs.oracle.com/en/java/javase/21/troubleshoot/troubleshooting-memory-leaks.html)、[jcmd 命令说明](https://docs.oracle.com/en/java/javase/21/docs/specs/man/jcmd.html)。

## 客户端内存实验

实验使用 1.20.1 Forge 47.4.20、Java 17.0.18、GeckoLib 4.8.4、SmartBrainLib 1.15，Java 最大堆固定 3072 MiB。Echo Warrior 正式包 SHA-256：`049815e558ebf0033659df13709f704d010b63c5f0616761ffd5ff58c0109e79`。额外 TBF 0.2.4.1 包 SHA-256：`530c73c0106511c97345fe36142db40885a7987678e5c79733e878bea21c9d73`。

场景在独立 CATTEST 中创建五名正式绑定英灵，使用正常客户端渲染、服务器 tick、绑定事务和网络同步。额外测试调用正式收回/召唤 API 并补充夹具燃料；这属于自动事务压力测试，不声称是人工进行了同次数点击。界面实验经过正式召唤器菜单打开和原版关闭路径，TBF 使用其真实界面。

本轮客户端记录与临时诊断源码位于 `build/memory-investigation-2026-10-12/`。正式 JAR、游戏存档和诊断工具分别记录，没有把诊断器打包进模组。

## 当前结论与下一步

**本轮没有复现评论所称的持续内存膨胀，尚未定位到需要修复的代码根因。** 两组客户端累计 30 分钟采样、2000 次收放和 120 次界面循环均有证据，但不是单实例连续运行一小时。

不能据此否定反馈，也不能宣布所有版本没有泄漏：本轮持续内存实验限于 1.20.1 Forge、指定依赖、小型隔离世界和 3 GiB 最大堆。1.21.1 只完成了常规服务端回归；26.1.2、反馈者整合包、原存档、较大堆设置、真实多人以及满一小时后的现象均未在本轮复现。

继续定位最需要反馈者提供：

1. Minecraft 版本、加载器与版本、Echo Warrior JAR 文件名、Java 版本和 `-Xmx` 等启动参数。
2. 模组列表或整合包导出，是否安装 TBF/其版本。
3. 出现问题时的 `latest.log`；32 GB 指游戏 Java 进程还是全系统内存。
4. 触发前的活动：大范围探索、同时存在的英灵数量、战斗、召唤器/TBF 界面、反复换世界。能提供问题发生时的 JFR 或堆转储时，再按实际保留对象定位；不根据总内存数字猜改代码。
